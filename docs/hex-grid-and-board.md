# Hexagonal Grid & Board Topology

This document details the mathematical coordinate system, projection geometry, canonical topological hashing, and graph data structures utilized to represent the Catan board in **Colonist Gambit**.

---

## 1. Hexagonal Coordinate System: Cube Coordinates

Colonist Gambit models the board using **Cube Coordinates** $(q, r, s)$ on a planar slice of 3D integer space $\mathbb{Z}^3$.

### The Fundamental Invariant
Every valid hex coordinate must satisfy the zero-sum plane invariant:

$$q + r + s = 0$$

```
           +s  -r
             \ /
       -q ----+---- +q
             / \
           +r  -s
```

### Conversions Between Axial and Cube
While axial coordinates $(q, r)$ save memory by omitting the third dimension, cube coordinates preserve symmetry across all 3 primary axes (which makes rotations, reflections, neighbor vectors, and distance formulas clean and uniform).

Conversion functions in `packages/shared/src/maps/coordinates.ts`:
- **Axial to Cube**:
  $$q = \text{axial}.q, \quad r = \text{axial}.r, \quad s = -q - r$$
- **Cube to Axial**:
  $$q = \text{cube}.q, \quad r = \text{cube}.r$$

### Neighbor Vectors
A pointy-topped hexagon has 6 adjacent neighbors. In clockwise order starting from the upper-right (direction 0):

$$\begin{aligned}
\vec{d}_0 &= (+1, -1, 0) \\
\vec{d}_1 &= (+1, 0, -1) \\
\vec{d}_2 &= (0, +1, -1) \\
\vec{d}_3 &= (-1, +1, 0) \\
\vec{d}_4 &= (-1, 0, +1) \\
\vec{d}_5 &= (0, -1, +1)
\end{aligned}$$

Neighbor coordinate at direction index $i$:
$$C_{\text{neighbor}} = C + \vec{d}_{(i \pmod 6 + 6) \pmod 6}$$

### Manhattan Distance on Hex Grid
The distance between two hexes $A$ and $B$ is half the sum of absolute coordinate differences:

$$\text{distance}(A, B) = \frac{|A.q - B.q| + |A.r - B.r| + |A.s - B.s|}{2}$$

## 2. Screen Pixel Projection (Pointy-Topped Hexagons)

Colonist Gambit uses **Pointy-Topped** hex orientation (points at top and bottom, flat edges at sides).

### Center Projection Matrix
Given hex circumradius $R$ (distance from center to any corner vertex), the Cartesian center coordinates $(x, y)$ are projected from cube coordinates $(q, r, s)$ using:

$$\begin{bmatrix} x \\ y \end{bmatrix} = R \begin{bmatrix} \sqrt{3} & \frac{\sqrt{3}}{2} \\ 0 & \frac{3}{2} \end{bmatrix} \begin{bmatrix} q \\ r \end{bmatrix}$$

Expanded:
$$x = R \left( \sqrt{3} q + \frac{\sqrt{3}}{2} r \right)$$
$$y = R \left( \frac{3}{2} r \right)$$

### Corner Vertex Pixel Computation
For a hex with pixel center $(x_c, y_c)$ and circumradius $R$, the 6 polygon corner vertices are located at angles $\theta_i$ for $i \in \{0, 1, 2, 3, 4, 5\}$:

$$\theta_i = \frac{\pi}{180} \cdot (60^\circ \cdot i - 30^\circ)$$

$$x_i = x_c + R \cos(\theta_i)$$
$$y_i = y_c + R \sin(\theta_i)$$

Starting at $-30^\circ$ (or $330^\circ$) places corner 0 at the top-right, corner 1 at the bottom-right, corner 2 at the bottom, corner 3 at the bottom-left, corner 4 at the top-left, and corner 5 at the top.

## 3. Canonical Topological Hashing

In board games played on hex grids, roads are placed on **edges** and settlements/cities are placed on **vertices**. 

### The Boundary Deduplication Problem
- Each internal **vertex** is shared by up to **3 touching hexes**.
- Each internal **edge** is shared by **2 touching hexes**.

If vertices and edges were stored as local sub-properties of individual hexes, duplicate entries would be created, leading to synchronization bugs and spatial floating-point rounding mismatches.

### Canonical Vertex Identification (`VertexId`)
Colonist Gambit solves this by defining the canonical ID of any vertex as a lexicographically sorted tuple of the up to 3 touching hex cube coordinates.

For a pointy-topped hex with center $C$, its corner at index $i$ touches:
1. The host hex: $C$
2. Neighbor 1: $C + \vec{d}_i$
3. Neighbor 2: $C + \vec{d}_{(i+1) \pmod 6}$

```typescript
function getCanonicalVertexId(touchingCoords: readonly CubeCoord[]): VertexId {
  const sorted = [...touchingCoords].sort((a, b) => {
    if (a.q !== b.q) return a.q - b.q;
    if (a.r !== b.r) return a.r - b.r;
    return a.s - b.s;
  });
  const coordStrings = sorted.map((c) => `${c.q},${c.r},${c.s}`);
  return `v:${coordStrings.join('|')}`;
}
```

Because coordinate sorting is deterministic, regardless of which of the 3 touching hexes evaluates corner $i$, the resulting `VertexId` string is identical.

### Canonical Edge Identification (`EdgeId`)
An edge connects two adjacent canonical vertices $V_1$ and $V_2$. The canonical `EdgeId` is generated by sorting the two vertex ID strings:

```typescript
function getCanonicalEdgeId(vertexIdA: VertexId, vertexIdB: VertexId): EdgeId {
  const [first, second] = vertexIdA < vertexIdB ? [vertexIdA, vertexIdB] : [vertexIdB, vertexIdA];
  return `e:${first}--${second}`;
}
```

## 4. The `CatanBoard` Graph Structure

The complete board graph is stored as an index of entities and dual-adjacency maps in `packages/shared/src/types/board.ts`:

```typescript
export interface CatanBoard {
  // Primary Entity Dictionaries
  readonly hexes: Record<HexId, HexTile>;
  readonly vertices: Record<VertexId, Vertex>;
  readonly edges: Record<EdgeId, Edge>;

  // Adjacency Indices for Fast O(1) Traversal
  readonly vertexAdjacentVertices: Record<VertexId, VertexId[]>; // 2 to 3 neighboring vertices
  readonly vertexAdjacentEdges: Record<VertexId, EdgeId[]>;       // 2 to 3 incident edges
  readonly edgeAdjacentVertices: Record<EdgeId, [VertexId, VertexId]>; // 2 boundary vertices
  readonly hexAdjacentVertices: Record<HexId, VertexId[]>;         // 6 corner vertices
  readonly hexAdjacentEdges: Record<HexId, EdgeId[]>;             // 6 perimeter edges

  readonly robberHexId: HexId;
}
```

### Entity Schemas
- **`HexTile`**:
  - `id`: e.g. `"hex:0,0,0"`
  - `coord`: `{ q: 0, r: 0, s: 0 }`
  - `terrain`: `'lumber' | 'brick' | 'wool' | 'grain' | 'ore' | 'desert'`
  - `numberToken`: `number | null` (2 to 12; `null` for desert)
  - `hasRobber`: `boolean`
- **`Vertex`**:
  - `id`: Canonical string (e.g. `"v:0,-1,1|0,0,0|1,-1,0"`)
  - `hexCoords`: Array of 1 to 3 touching hex cube coordinates
  - `building?`: `{ type: 'settlement' | 'city', playerId: PlayerId }`
  - `harbor?`: `{ type: 'generic' | ResourceType, ratio: number }`
- **`Edge`**:
  - `id`: Canonical string (e.g. `"e:v:...--v:..."`)
  - `vertexIds`: `[VertexId, VertexId]`
  - `road?`: `{ playerId: PlayerId }`

## 5. Procedural Spiral Map Generation

Board generation is handled by `generateBoard()` in `packages/shared/src/maps/generator.ts`.

### Spiral Generation (Radius 2)
To generate the 19 hexes of the standard base board, all coordinates satisfying $\text{distance}((0,0,0), (q,r,s)) \le 2$ are enumerated:

```typescript
export function generateSpiralCoords(radius: number): CubeCoord[] {
  const coords: CubeCoord[] = [];
  for (let q = -radius; q <= radius; q++) {
    const r1 = Math.max(-radius, -q - radius);
    const r2 = Math.min(radius, -q + radius);
    for (let r = r1; r <= r2; r++) {
      const s = -q - r;
      coords.push({ q, r, s });
    }
  }
  return coords;
}
```

### Resource & Chit Distribution
The standard 19-tile board includes:
- **Terrains**: 4 Lumber (Forest), 4 Wool (Pasture), 4 Grain (Fields), 3 Brick (Hills), 3 Ore (Mountains), 1 Desert.
- **Tokens**: `[2, 3, 3, 4, 4, 5, 5, 6, 6, 8, 8, 9, 9, 10, 10, 11, 11, 12]` (tokens 6 and 8 are styled red due to highest rolling probability $5/36$).
- **Robber**: Placed initially on the Desert hex (`numberToken = null`).

### Deduplicated Graph Linking
During iteration over the 19 hexes:
1. For each hex, 6 corner `VertexId`s are computed via `getVertexIdForHexCorner`. If not yet recorded, a new `Vertex` is created; otherwise, the hex coordinate is appended to `vertex.hexCoords`.
2. For each consecutive pair of corners $i$ and $(i+1) \pmod 6$, an `EdgeId` is generated. If new, the edge is instantiated, and bidirectional adjacency indices (`vertexAdjacentVertices`, `vertexAdjacentEdges`, `edgeAdjacentVertices`) are populated.
3. This creates a fully connected graph topology consisting of **19 Hexes, 54 Vertices, and 72 Edges**.
